# ADR-001: Port spectrik from Python to Go

**Date**: 2026-09-17
**Status**: Proposed
**Deciders**: jheddings

## Context

spectrik is a small library (about 900 lines of source) that provides a
specification/blueprint/project model for declarative configuration-as-code
tools, with HCL as the configuration language. It is published on PyPI, but
the only known consumers are three tools on the same system:

| Consumer | Purpose | Spec types | Talks to |
| -------- | ------- | ---------- | -------- |
| machina | macOS machine bootstrap | 12 | brew, launchctl, defaults, git, npm |
| kodex | GitHub repo configuration | 7 (+1 project type) | GitHub REST (PyGithub), git (GitPython), 1Password CLI |
| rise/red infra | Supabase, Railway, GitHub env config | 27 (+5 project types) | Supabase Management API, Railway API, GitHub REST, psycopg2, 1Password CLI |

No external consumers are known.

### Prior art: go-spec and the Go-era consumers

Both machina and kodex were Go programs before they were Python programs,
and both were built on a Go library called `go-spec`
(`github.com/jheddings/go-spec`). The GitHub repository has since been
deleted, but two tagged versions survive in the local Go module cache
(`v0.0.3` and `v0.1.0`), and the Go-era consumer code is in each repo's
git history.

| Date | Event |
| ---- | ----- |
| 2025-08-26 | kodex (then `proj-cli`) starts in Go |
| 2025-10-10 | go-spec v0.0.3 tagged |
| 2025-11-03 | machina (then `sysconfig`) converted to go-spec |
| 2026-02-03 | kodex ported back to Python, using a Python DSL for blueprints |
| 2026-02-15 | go-spec v0.1.0 tagged: a full redesign, four pseudo-versions the same day |
| 2026-02-15 | Renovate bumps machina to go-spec v0.1.0; the API change breaks the build |
| 2026-02-16 | kodex replaces its Python DSL with HCL files (`python-hcl2`) |
| 2026-02-17 | spectrik created by extracting kodex's model and HCL loader |
| 2026-02-20 | machina ported to Python on spectrik |

**Neither Go version had HCL.** Configuration was Go code. Blueprints and
projects lived under `config/bp/*.go` and `config/proj/*.go`, registered
from `init()` functions through a builder API:

```go
spec.RegisterProject(
    spec.NewProject("wxdat").
        WithDescription("Weather data collector.").
        WithPath("jheddings/wxdat").
        WithBlueprint(*bp.PublicRepo()).
        WithBlueprint(*bp.RenovateCI()).
        Build(),
)
```

machina layered `viper` on top so a local YAML file could override values
that blueprints read at construction time, with `WithDeferredSpec` closures
to delay evaluation. That was the extent of "configuration as data" in the
Go era, and it was the pain point: adding a machine or a repo meant writing
Go, and the kodex HCL design doc of 2026-02-16 names replacing the code DSL
with declarative files as its goal.

**go-spec v0.0.3** (what the apps actually ran on) had a `Specification`
interface of `Check` and `Apply`, with `RemovableSpec` and `ReplaceableSpec`
as optional interfaces detected by type assertion, and `EnsureSpec`,
`ReplaceSpec`, `RemoveSpec` wrappers. Registries were package-level globals
with mutexes. Specs received `*spec.Project`, whose fields were fixed
(`Name`, `Desc`, `Path`, `URL`).

**go-spec v0.1.0** (tagged two days before spectrik, never adopted by any
consumer) was a redesign toward file-driven configuration. It has no
dependencies and no parser, but its shape is instructive because it is the
Go design the author reached for immediately before switching to Python:

- `Spec` interface: `Exists`, `Diff`, `Apply`, `Remove`, each taking a
  `context.Context` and a `Target`.
- `Diff` is a structured list of `FieldDiff{Name, Current, Desired}`, not a
  boolean. spectrik's `equals()` is a regression from this.
- `Op` interface with `Present`, `Replace`, `Remove` strategy structs.
  Dry-run is a `context.Context` value.
- `Blueprint.Include []string` and `Project.Use []string`, documented as
  "resolved to other blueprints by name during loading". These are exactly
  spectrik's `BlueprintRef.includes` and `ProjectRef.use`.
- `DecoderRegistry` mapping a type name to `func(body map[string]any)
  (Spec, error)`. This is spectrik's `_spec_registry` plus the
  `spec_cls(**attrs)` call.
- `ResolverRegistry` mapping URI schemes to resolvers, intended for
  `op://` secrets. spectrik never got this; kodex issue #274 (open) asks
  for it.
- `Target` interface with `Name()` and `Var(key)`, decoupling specs from
  the concrete project type.

The Python switch happened at the point where a parser and a loader would
have been the next step. The kodex HCL design doc chose `python-hcl2` and
listed expression evaluation and interpolation as explicit non-goals.
Interpolation and `variable` blocks were added to spectrik afterward, which
is how the hand-written resolver came to exist.

### What the library actually spends its code on

Roughly a third of spectrik exists to make HCL work in Python. python-hcl2
is a third-party Lark grammar, not a reference implementation, and the
library works around it in several places:

- `hcl.py` unwraps heredoc tokens with a regex and dedents `<<-` bodies by
  hand, because python-hcl2 emits them raw.
- `resolve.py` is a hand-written `${...}` interpolation engine: dotted-path
  traversal, type preservation for whole-string refs, callable invocation,
  `$${...}` escaping, and a load-bearing regex constraint that keeps GitHub
  Actions `${{ }}` expressions from being interpreted.
- Errors carry a file path at best. There is no line or column information
  because the parser does not expose it in a usable form.
- `variable` / `variables` blocks are extracted and resolved manually before
  the rest of the document is walked.

### How consumers use the library

The consumers exercise a narrow slice of the API. Across all three:

- Every spec is a plain class (dataclass or keyword-only `__init__`);
  none is a Pydantic model. Attribute validation is ad hoc inside methods.
- All three subscribe to the same five context events (`on_spec_start`,
  `on_spec_applied`, `on_spec_removed`, `on_spec_skipped`, `on_spec_failed`)
  via `+=` to drive a TUI.
- Only rise/red uses `@pre_build` hooks (1Password secret resolution).
  Nothing uses `@post_build`.
- Only rise/red and kodex subclass `Project`. kodex pops spectrik's private
  `_project_registry` to replace the base `"project"` block type.
- kodex reuses `Resolver` on non-HCL template files (GitHub workflow YAML)
  and parses its own `variables.hcl` with raw `hcl2` before calling `scan`.
- Interpolation in consumer HCL is exclusively `${var.*}` and `${env.*}`.
  No consumer HCL uses functions, conditionals, for-expressions, or `$${`.
  Nine heredocs exist, all in kodex and rise/red.
- No consumer spec reads `ctx.dry_run`; dry-run is handled entirely by the
  strategy layer.
- machina's specs never read `ctx` at all.

## Decision

Port spectrik to Go as a new module, designed around `hashicorp/hcl/v2` and
`gohcl` rather than transliterated from the Python package. Leave the Python
package published and frozen at its current version. Port consumers one at a
time, machina first, and treat each consumer port as a pressure test that may
revise the Go API.

This is a proposal. The design decisions in the trade-off section below must
be settled explicitly before code is written.

## Options Considered

### Option A: Stay in Python

| Dimension | Assessment |
| --------- | ---------- |
| Complexity | Low (no change) |
| Cost | None now; ongoing python-hcl2 workaround maintenance |
| Task fit | Medium: HCL is second-class, diagnostics are weak |
| Team familiarity | High |

**Pros**

- Nothing to port. All three consumers keep working.
- Spec authoring is fast: small glue classes over CLIs and REST APIs.
- Loosely typed attributes (`Any` values, `list | dict | None` shapes) are
  natural.

**Cons**

- The HCL layer will always be a workaround layer. Position-aware
  diagnostics, real expression evaluation, and spec-conformant parsing
  are not available without reimplementing them.
- machina, a machine-bootstrap tool, requires Python and uv to be installed
  before it can run. That is a chicken-and-egg problem for its purpose.
- Registration by import side effect and mutable global registries make
  tests fragile (every test must save/clear/restore `_spec_registry`).

### Option B: Port to Go, greenfield design around gohcl

| Dimension | Assessment |
| --------- | ---------- |
| Complexity | Medium: library is small, but semantics change |
| Cost | Library port plus three consumer ports and test redesign |
| Task fit | High: HCL is native, the model maps to interfaces cleanly |
| Team familiarity | Medium: Go is in active use in four other repositories |

**Pros**

- `hcl.py` and `resolve.py` largely disappear. The parser handles heredocs,
  escaping, and expressions; `gohcl` decodes bodies into tagged structs;
  `hcl.Diagnostics` carries file, line, and column.
- Two awkward Python idioms become cleaner Go idioms: the `NotImplemented`
  tri-state from `equals()` becomes an optional interface (the `io.WriterTo`
  pattern), and `@pre_build` / `@post_build` via MRO scan become optional
  `PreBuilder` / `PostBuilder` interfaces on the project type.
- `Project` subclassing becomes struct embedding, and consumer fields decode
  directly from the block body with diagnostics, instead of a leftover
  attribute dict splatted into a constructor.
- Exceptions plus a boolean build result become plain `error` returns.
- machina becomes a static binary and can use go-cfprefs directly for its
  macOS preference specs.
- Registries become explicit types with a default instance (the
  `http.DefaultServeMux` pattern), which removes the test fixture dance and
  makes kodex's registry override a supported operation.
- go-spec v0.1.0 already sketches the target shape: `Op` strategies,
  optional spec interfaces, `Include` / `Use` by name, a decoder registry,
  and a resolver registry. The port is not starting from zero on design.

**Cons**

- Each Go spec is a struct with tags, four methods, and explicit error
  handling. Across roughly 46 consumer spec types this is real, bounded
  boilerplate.
- Loosely typed attributes need `cty.Value` handling or type switches.
  machina's `macos_pref.value` (bool/int/string) and `launchd_agent.calendar`
  (list or map) are the concrete cases. kodex's tri-state booleans become
  pointer booleans.
- Consumer tests lean heavily on monkeypatching (40 occurrences in machina
  alone). Idiomatic Go needs small interfaces and fakes for the GitHub
  client, subprocess execution, and the filesystem.
- kodex's template rendering of non-HCL files needs its own substitution
  path; the HCL evaluator does not apply to arbitrary text.

### Option C: Port to Go by transliterating the Python structure

Rejected. Mirroring `hcl.py` / `resolve.py` in Go would reimplement what
`hashicorp/hcl` already does, and would carry the Python registry and
event shapes into a language where they are not idiomatic. The value of the
port comes from designing around the native HCL library.

### Option D: Revive go-spec v0.1.0 as-is

Rejected as a starting point, but its design is input to Option B. It was
never used by a consumer, has no loader, and its `DecoderRegistry` takes a
`map[string]any` body, which is the python-hcl2 shape rather than the
`hcl.Body` shape that `gohcl` decodes from. Adopting it unchanged would
recreate the Python loader's problems in Go.

## Trade-off Analysis

The decisive factor is task fit, not effort. The library's job is to load
HCL into a typed spec/blueprint/project model and execute it. In Python that
job is mostly workaround; in Go it is mostly configuration of an existing,
spec-conformant library. The remaining core (strategies, blueprints,
projects, context, events) is under 400 lines and maps to Go interfaces
without loss.

The cost lands on the consumers, not the library. Spec authoring gets more
verbose and consumer tests need restructuring. That cost is bounded and is
also the point of "porting slowly and idiomatically."

### Settled decisions

Two compiling spikes were built and compared before choosing (an
interface-target design and a generic-spec design, each with two project
types in one workspace and a wrong-target test). The outcome:

- **Specs are generic over their project type; ops are not.**
  `Spec[P Target]` has `Apply(ctx context.Context, t P) error`. Consumer
  methods receive their concrete project with no assertion. Strategies
  (`Ensure[P]`, `Present[P]`, `Absent[P]`) are generic but implement the
  non-generic `Op` interface, which is the erasure point that lets one
  blueprint or workspace hold ops for different project types. The single
  type assertion lives in the strategy's `Run`, in library code, with one
  error message.
- **`Target` is an interface with one method, `Base() *Project`.**
  Consumers embed `spectrik.Project` and satisfy it for free. A pure
  transliteration with `Blueprint[P]` / `Workspace[P]` was rejected because
  rise/red has five project types in one workspace.
- **Comparison is a boolean.** Optional `Comparer[P]` with
  `Equals(ctx, t) (bool, error)`. A structured diff was considered and
  set aside as not worth the per-spec cost today.
- **Optional behaviour is an optional interface**: `Comparer[P]`,
  `Exister[P]`, `Remover[P]`. Fallback chain as in Python: `Exists` falls
  back to `Equals`, then to "absent". `Ensure` on a spec with no
  `Comparer` always applies.
- **Registration is a package-level generic function**,
  `RegisterSpec(reg, name, func() Spec[P])`, because Go methods cannot have
  type parameters. Duplicate names panic, as `net/http` does for duplicate
  patterns.
- **Building is a package function**, `Build(ctx, target)`, not a method on
  `Project`, because an embedded struct cannot see the struct that embeds
  it.
- **Dry-run rides the `context.Context`** via `WithDryRun` / `IsDryRun`,
  as go-spec v0.1.0 did. Specs never see it; strategies do.
- **Hooks are a struct of optional func fields on the context**,
  `WithHooks(ctx, *Hooks)`, in the style of `httptrace.ClientTrace`. Each
  callback receives an `Event{Strategy, Spec, Target}`; the spec value is
  the consumer's pointer, so it doubles as a correlation key. Every run
  fires `SpecStart` and `SpecFinish`, with exactly one of `SpecApplied`,
  `SpecRemoved`, `SpecSkipped(reason)`, or `SpecFailed(err)` between them.
- **Continue-on-error is a context flag**, `WithContinueOnError`. When
  set, `Blueprint.Build` and `Build` run everything and return
  `errors.Join` of the failures, each wrapped with its blueprint and
  project name. The default stops at the first error.
- **Registry decoding is HCL-agnostic.** `Registry.NewOp(name, strategy,
  decode)` takes a `Decoder` callback that fills the freshly constructed
  spec; the HCL loader supplies one built on `gohcl`.
- **No project type is registered by default.** A consumer that wants
  plain `project` blocks registers `*spectrik.Project` under that name.
  This removes the need for the registry override kodex relied on.
- **Interpolation is real HCL evaluation.** The loader builds an
  `hcl.EvalContext` per file from the caller's `Options.Variables` and
  `Options.Functions`, with `var` populated from that file's `variable`
  and `variables` blocks in source order. Variables are file-scoped, as in
  Python, because rise/red defines the same names with different values
  in sibling files. A caller-supplied `var` is merged beneath the file's
  own. `EnvVars()` is the one helper shipped, for `env`. No functions are
  provided unless the caller passes them. `${{` must be written `$${{`.
- **Spec and project attributes decode through `gohcl` struct tags.**
  Unknown or missing attributes fail at load time with file, line, and
  column. The loader decodes the base project fields (label, description,
  use, strategy blocks) itself and hands the remaining body to the
  consumer struct, because `gohcl` does not flatten embedded structs.
- **Load validates everything.** Unknown spec types, bad attributes,
  dangling `use` / `include` references, circular includes, and
  duplicate names all fail in `Load` as `hcl.Diagnostics`.
- **Workspace resolves on access.** `ws.Project(name)` and
  `ws.Blueprint(name)` decode a fresh value from the retained block each
  call, so a target mutated by a lifecycle hook or a build does not leak
  into the next build.
- **Lifecycle hooks are optional interfaces**, `PreBuilder` and
  `PostBuilder`. `PreBuild` aborts the build on error; `PostBuild` always
  runs, even after a `PreBuild` failure, and its error is joined.

### Design decisions still to settle

Each of these is a semantic change. They should be explicit choices, not
accidents of porting. Items 1 through 8 and 11 are settled above and are
kept below only for the record; 9 and 10 remain open and will be decided
when the first consumer port reaches them.

1. **Interpolation becomes real HCL evaluation.** `${var.x}` is a template
   expression evaluated against an `hcl.EvalContext`. Functions,
   conditionals, and for-expressions become available. Any literal `${{`
   must be written `$${{`. No consumer HCL file contains `${{` today.
   Decide whether `var` and `env` are the only root names or whether
   consumers can register arbitrary variables and functions.
2. **Variables become first-class.** `variable` / `variables` blocks should
   populate the `EvalContext` rather than be pre-extracted by hand. kodex
   currently parses its own `variables.hcl`; decide whether a workspace-level
   variables file is a library feature.
3. **Registry becomes a type.** `Registry` with `RegisterSpec` /
   `RegisterProject` and a package-level default. Decide whether
   re-registering a name is an error, an override, or requires an explicit
   `Override` call. kodex needs the base `"project"` type to be replaceable.
4. **Optional-interface contract for specs.** The required interface is
   `Apply`. Optional interfaces: `Comparer` (`Equals`), `Exister`
   (`Exists`), `Remover` (`Remove`). Strategies type-assert. Decide the
   fallback chain (today: `Exists` falls back to `Equals`, and unknown
   equality falls back to "absent"). go-spec v0.0.3 used this exact
   pattern (`RemovableSpec`, `ReplaceableSpec`), so it has precedent here.
   Also decide whether comparison returns a boolean or a structured `Diff`
   as in go-spec v0.1.0. A structured diff is what a `plan` command and the
   TUI want, and the rise/red `plan` subcommand already exists.
5. **Events become a hooks struct** of optional func fields, in the style of
   `httptrace.ClientTrace`. Every consumer subscribes to the same five
   events, so this is a direct match. Decide whether hooks live on `Context`
   or are passed separately.
6. **Errors replace exceptions.** `Build` returns `error`. Decide whether
   `continue_on_error` collects via `errors.Join` or whether the caller
   handles per-spec results through hooks. The existing
   `docs/specs/2026-03-09-build-result-design.md` is relevant input.
7. **Workspace resolve semantics.** The Python workspace builds a fresh
   project instance on every access. Decide whether Go resolves once and
   caches (the natural Go shape) and whether anything depends on fresh
   instances.
8. **Attribute typing.** Decide whether specs receive decoded Go values via
   `gohcl` tags (strict, recommended) or raw `cty.Value` for the handful of
   polymorphic attributes.
9. **Template substitution outside HCL.** kodex renders workflow files with
   `${var.x}` substitution. Decide whether the Go library offers a small
   string-substitution helper or whether kodex owns this.
10. **Secret resolution.** All three consumers resolve `op://` URIs
    themselves, each with its own subprocess wrapper. go-spec v0.1.0 had a
    `ResolverRegistry` keyed by URI scheme, and kodex issue #274 asks for
    the same thing in spectrik. Decide whether this is a library concern
    (a resolver registry consulted during decoding or at apply time) or
    stays in consumers.
11. **Spec target coupling.** go-spec v0.1.0 introduced a `Target`
    interface so specs did not depend on a concrete project struct. Python
    specs take `Context[P]` and read `ctx.target` fields directly. Decide
    whether Go specs receive the concrete embedded project type via a
    generic `Context[P]`, or an interface.

## Consequences

**Easier**

- Position-aware error messages for every HCL problem.
- Spec-conformant HCL, including expressions and functions, with no
  library-side parsing code.
- Static binaries for all three tools. machina no longer needs a Python
  toolchain on a fresh machine.
- Registries and hooks become explicit, testable types.

**Harder**

- Spec authoring is more verbose.
- Consumer tests must be restructured around interfaces and fakes.
- Two languages during the transition, and the Python package must stay
  frozen and installable until the last consumer moves.

**To revisit**

- Whether the Python package is deprecated on PyPI once all consumers have
  moved, or left published indefinitely.
- Whether rise/red infra moves at all. It lives inside a TypeScript repo and
  would remain a second language either way.
